# movie_stat_db 数据库检查与修复报告

> 检查日期：2026-09-15
> 目标库：`movie_stat_db`（MySQL，192.168.184.134:3306，部署于 VMware WorkStation 中的 Ubuntu 虚拟机）
> 预期数据基准：本项目 `/db` 目录下 13 个 SQL 文件（`movie_stat_db.sql` 为建表脚本，其余 12 个为各统计表的数据插入脚本）

---

## 1. 背景与目标

- 数据管道：`MovieAnalysis.py`（PySpark，提交至 YARN）从 HDFS 读取 `movies.csv` 完成统计 → 结果 CSV 落盘 HDFS `/movies/analysis_results/<表名>/` → Sqoop 导出至 MySQL `movie_stat_db` → 前端 ECharts 读库渲染。
- `/db` 下的 SQL 文件代表**数据库最终应具备的正确数据**（已清洗归一后的版本）。
- 已知线索：功能8（`stat_year_region_count`，每年各国发行量对比）与功能B（`stat_year_top20_movie`，每年豆瓣评分 Top20）数据存在问题。
- 本次目标：全库比对检查所有表是否符合预期，并使用 `/db` 下的 SQL 文件修复不一致的表。

### 2.2 比对策略（两级）

| 级别 | 方法 | 用途 |
|---|---|---|
| 一级：行数比对 | 逐表执行 `SELECT COUNT(*)`，与对应 SQL 文件的 insert 行数比对 | 快速定位所有不符预期的表 |
| 二级：行集合比对 | 解析 SQL 文件中每条 insert 的 values 元组，与库中 `SELECT *` 结果做多重集合差集（Python `collections.Counter`） | 定位具体差异行：库中多出的行（多余/脏数据）与缺少的行 |

### 3.2 逐表差异分析（二级行集合比对）

#### （1）`stat_year_region_count`（功能8）——数据基本全丢，仅剩 1 行脏数据

- 库中仅剩 1 行：`(movie_year=2049, region_name='美国', region_year_count=1)`。
- 库内最小/最大年份均为 2049，而预期数据年份范围为 1873 起的完整 5421 行。
- 推断原因：Sqoop 导出该表时任务失败（或导入了脏分区文件），最终只成功写入了一条未来年份（2049）的异常记录。源数据中 `YEAR` 为脏值 "2049" 未被 `YEAR != 0` 的过滤条件拦截（脚本仅过滤了 0 和 NULL）。

#### （2）`stat_year_top20_movie`（功能B）——缺 149 行

- 库中 1819 行 vs 预期 1968 行，缺失的行集中在**电影名含特殊字符**（英文逗号、引号、冒号等）的记录。
- 推断原因：Sqoop 按逗号分隔字段导出时，含分隔符/引号的片名导致行解析错位或被跳过。虽然 Spark 写出时开启了 `quote/escape`，但导入端对部分边界字符（如名称中的转义引号）处理失败，造成部分行丢失。
- 存量数据本身（如 `movie_year=0` 的 20 行）与预期文件一致，属于 Spark 脚本未过滤 `YEAR="0"` 的已知行为，本次不改数据。

#### （3）`stat_region_count`（功能4）——双空格变体脏行 + 计数偏差

行集合比对结果：库中多出 39 行、缺少 27 行（净多 12 行）。差异分两类：

- **变体脏行**：源数据 REGIONS 中存在连续空格分隔（如 `印度  India`，两个空格），Spark 按单空格模式 `' / '` split 后未命中，产生了与正常行（`印度 India`）**分裂的两条记录**：
  - 多出：`('印度  India', 7)`、`('印度  Indian', 3)`、`('丹麦  Denmark', 2)`、`('俄罗斯  Russia', 2)` 等
- **计数偏差**：同名行的计数与预期版本不一致，例如：
  - 库中 `('西班牙', 4179)` vs 预期 `('西班牙', 4180)`
  - 库中 `('印度 India', 508)` vs 预期 `('印度 India', 515)`
  - 库中 `('加拿大 Canada', 284)` vs 预期 `('加拿大 Canada', 285)`
  - 库中 `('俄罗斯 Russia', 67)` vs 预期 `('俄罗斯 Russia', 69)`

  即库中为**未归一化清洗的原始统计**，而 `/db` 的 SQL 是**清洗合并后（变体地区名已并入主名称）的最终版本**。

#### （4）`stat_language`（功能10）——同类双空格变体问题

库中多出 28 行、缺少 19 行（净多 9 行）：

- 变体脏行：`('印地语  Hindi', 5)`、`('印地语   Hindi', 2)`（三空格）、`('丹麦语 Dansk', 3)`、跨语言粘连行 `('意大利语  英语', 2)`、`('匈牙利语  德语', 2)` 等
- 计数偏差：`('印地语 Hindi', 113)` vs 预期 `120`、`('葡萄牙语 Portuguese', 39)` vs 预期 `41` 等

#### （5）`stat_region_year_avg_score`（功能9）——2 行均值不一致 + 变体脏行

- 均值偏差（聚合口径不同）：
  - 库中 `('西班牙', 2013, 6.529629629629629)` vs 预期 `('西班牙', 2013, 6.535714285714285)`
  - 库中 `('印度 Indian', 2013, 6.0)` vs 预期 `('印度 Indian', 2013, 6.1)`
- 变体脏行：`('印度  Indian', 2013, 6.2)` 未并入主名称

**共同根因总结**：库中数据为 Sqoop 直接导入的**未经清洗归一**的原始统计结果；多值字段（REGIONS/LANGUAGES）中含连续空格的脏值未被 `' / '` 分隔符正确拆分，导致同一地区/语言被拆成多条变体记录、部分计数偏低；功能8/功能B则分别存在导出失败与特殊字符行丢失问题。`/db` 下的 SQL 文件是这些问题全部修正后的权威版本。

## 4. 修复策略

- **原则**：以 `/db` 下 SQL 文件为唯一权威数据源，对不符预期的表整体替换，不做局部修补（局部修补需逐行 diff 且无法保证聚合口径一致，整体替换结果确定、可重复执行）。
- **操作**：对每张问题表执行 `TRUNCATE TABLE` 清空 → 逐行执行对应 SQL 文件中的 `insert into movie_stat_db.<表名> ... values (...)` 语句（每 1000 条提交一次事务，避免长事务）。
- **范围**：5 张表 —— `stat_year_region_count`（功能8）、`stat_year_top20_movie`（功能B）、`stat_region_count`、`stat_language`、`stat_region_year_avg_score`。
- **验证**：修复后重新执行全表行数比对，要求 13/13 全部 OK。

## 7. 遗留事项与改进建议

1. **功能B 保留 `movie_year=0` 的 20 行**：源数据 `YEAR="0"`（未上映/年份缺失）未被过滤（脚本窗口函数统计前仅过滤了评分）。该行为与预期 SQL 文件一致，属 Spark 脚本设计如此，未做改动；若业务上不希望出现"0年"，需在 `MovieAnalysis.py` 的 B 节 filter 中增加 `YEAR != 0` 条件后重跑。
2. **多值字段清洗建议**：若后续重跑 Spark 任务，建议在 split 前对 REGIONS/LANGUAGES 做空白归一（如 `regexp_replace` 将连续空格压成单个），从源头消除双空格变体行，避免再次出现 `印度  India` 类脏数据。
3. **YEAR 脏值过滤建议**：`YEAR != 0` 无法拦截 "2049" 这类异常年份，可增加合理年份范围校验（如 1800–当前年份）。
4. **Sqoop 导出健壮性**：功能B因特殊字符丢行的经验表明，Sqoop 导出含长文本/特殊符号字段（电影名）时应确保 `--input-optionally-enclosed-by '"'` 与 Spark 写出侧的 `quote/escape` 严格配对，导出后应以行数校验作为固定检查步骤。
5. **修复方式说明**：本次采用"SQL 文件整体重灌"方式，操作简单可靠；后续如再次出现单表少量差异，可考虑基于行集合 diff 的增量修复，但需注意聚合口径一致性。
